13/*
14 PULSE RTSP SESSION
15
16 Phase 1: input side only — dial out to an RTSP source (typically an IP
17 camera) and ingest its streams as PMX inputs.
18
19 RTSP is a *content source*, not a placement. A successfully-connected
20 session is identified by an opaque #PulseRtspSessionID that the caller
21 can subsequently:
22
23 - place into a video mix surface via
24 pulse_video_mix_input_from_rtsp_session() — possibly into multiple
25 surfaces, of multiple mixes, simultaneously;
26 - bind to a Pulse media-content slot (MAIN, PRESENTATION, …) via
27 pulse_rtsp_session_bind_to_content() so PMX wires the session's
28 audio/video into that role;
29 - leave un-placed and consume directly via the input ids returned
30 by pulse_rtsp_session_get_input_ids().
31
32 Multiple concurrent sessions are supported: the same client can dial
33 N different cameras and place each one independently.
34*/

220/*
221 PULSE RTSP STREAM ITERATOR
222
223 After pulse_rtsp_session_connect_input() returns success the camera's
224 SDP has been fully negotiated and every stream announced by the server
225 has been turned into its own input. The stream iterator surfaces
226 these as enumerable, named, individually-pickable handles — modelled
227 intentionally on the device iterator (#PulseDeviceIterator) so the
228 same UX that hosts a "pick a microphone" dropdown can host a "pick an
229 RTSP video sub-stream" dropdown with no architectural difference.
230
231 Lifetime: a #PulseRtspStreamID is only meaningful relative to its
232 owning #PulseRtspSessionID. Both become invalid the moment the
233 session is disconnected via pulse_rtsp_session_disconnect_input().
234 Iterators are snapshots — they survive subsequent stream changes
235 (none happen today; rtspsrc emits the full set up-front via
236 no-more-pads) but the stream pointers they hand out remain valid only
237 until pulse_rtsp_stream_iterator_free() is called.
238*/
